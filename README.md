# Interview Copilot

AI 面试伴侣的首个可运行纵向切片。它面向人工面试官，不替代最终招聘决策。

当前版本已经打通：

- 候选人、岗位、申请和业务 / HR / CEO 面试轮次；
- “我的今日面试”入口：按当前面试官、面试安排、候选人、岗位和轮次自动选择对应体系；
- HR 面试任务创建：一次录入候选人和岗位，并从业务/HR/CEO 面中任选 1–3 轮、自由排序和分配面试官；流程会保存为岗位默认值；
- 飞书 OAuth 2.0 登录边界：服务端换取用户身份、签名会话、按 `open_id` 精确分配面试；
- HR 招聘任务后台：任务列表、改期、改派、场景变更和取消；
- PDF、DOCX、TXT、Markdown 简历与 JD 文本导入（扫描 PDF 暂不含 OCR）；
- 每轮统一必问题、可选问题及必问题覆盖进度；
- 录音与 AI 分析告知硬门禁；
- WebSocket 逐字稿事件；
- 浏览器麦克风显式授权、单声道 16 kHz PCM 实时上传；
- Pipecat `InputAudioRawFrame` 音频帧桥接；
- WAV 录音、时长/峰值指标和录音元数据；
- 实时能力覆盖、可溯源的关键事实/风险/未知项和追问建议；
- 人工确认证据；
- 证据优先的评价草稿；
- 面试后的面试质量复盘：标准题覆盖、候选人表达占比、证据产出和人工四维评价；
- HR 面试质量分析看板：按面试官与岗位汇总质量趋势，并区分面试流程问题和招聘供给问题；
- 角色化行动中心：面试官查看今日面试、七天内准备项和待提交评价；HR 查看待排期、待补评价、可终审及知识审批；
- 飞书通知中心：排期通知、面试前提醒、待补评价、岗位流程终审和知识审批消息先预览后人工发送；
- 系统配置与试点就绪中心：区分本地演示和正式试点，统一检查身份、ASR、模型、数据库、存储、HTTPS 与知识库；
- 版本化岗位面试报告：管理层摘要与 HR 完整档案分层展示，支持锁定、历史版本、内部链接和打印为 PDF；
- 数据治理与审计中心：到期预览、HR 二次确认清理、原始材料脱敏和关键操作留痕；
- 知识更新提案与人工审批隔离；
- `boss-recruiting-agent` 统一输入契约；
- 腾讯云实时 ASR（可替换 Provider）、LLM、飞书和北森的适配边界。

当前已经支持真实麦克风收音、WAV 录音，以及可选的腾讯云实时 ASR。未配置密钥时界面会明确显示“已收音、未转写”；ASR 暂时不可用时录音也不会中断。手动逐字稿仍作为测试和故障降级入口。

## 本地启动

要求 Python 3.11+。

Windows 可以直接双击项目根目录的 `start-interview-copilot.cmd`，它会启动服务并打开网页。启动后的命令窗口需要保持开启。

```powershell
cd interview-copilot\backend
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev,voice]"
uvicorn app.main:app --reload
```

### 开启腾讯云实时字幕（PowerShell）

先在腾讯云开通语音识别服务并创建 API 密钥，然后在启动服务的同一个 PowerShell 窗口设置：

```powershell
$env:INTERVIEW_ASR_PROVIDER="tencent"
$env:TENCENT_ASR_APP_ID="你的 AppId"
$env:TENCENT_ASR_SECRET_ID="你的 SecretId"
$env:TENCENT_ASR_SECRET_KEY="你的 SecretKey"
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

默认使用 `16k_zh_en_speaker_2.0` 中英混合话者分离大模型，与腾讯云实时语音识别 2.0 资源包匹配。系统先按声源聚类，再以对话语义自动映射面试官与候选人；低置信度内容保持待确认。密钥只保存在服务端环境变量中，不会传给浏览器、写进数据库或返回给前端。

打开 <http://127.0.0.1:8000>，点击“进入今日面试”。

当前本地演示使用“当前面试官”身份。正式接入时，身份由飞书或企业 SSO 解析；系统再从面试安排找到该面试官今天的场次，并沿着“申请记录 → 候选人和岗位 → 业务/HR/CEO 轮次 → 版本化能力模型与题库”加载对应工作台。前轮只带入已确认事实和待验证问题，不直接展示前轮分数与录用建议。

### 开启真实 AI 分析（部署时）

系统默认使用本地规则模式，不会把面试内容发送给外部模型。后端现已支持 OpenAI 兼容的 Chat Completions 接口；后续确定模型供应商后，在服务器环境变量中配置即可，不需要修改面试官页面：

```powershell
$env:INTERVIEW_PROVIDER_MODE="production"
$env:INTERVIEW_LLM_BASE_URL="https://你的模型网关/v1"
$env:INTERVIEW_LLM_API_KEY="仅保存在服务器的 API Key"
$env:INTERVIEW_LLM_MODEL="deepseek-v4-flash"
$env:INTERVIEW_LLM_PLANNING_MODEL="deepseek-v4-pro"
$env:INTERVIEW_LLM_TIMEOUT_SECONDS="12"
```

实时分析只接收当前岗位、能力项和必要的逐字稿上下文，不发送候选人姓名、联系方式或完整简历。面试前深度出题会读取脱敏后的简历正文与 JD，用于找到值得验证的真实经历。模型输出必须是结构化 JSON；任何证据引文都必须逐字存在于原始候选人片段中，且引用的片段和能力项必须属于当前面试，否则不会入库。单次或连续两次远程失败时页面显示“AI 语义分析重试中”；连续三次失败才显示语义服务暂不可用，下一次成功分析会自动恢复为在线状态，不中断录音、字幕和人工面试。

实时追问采用“语义理解 + 公司行为标准 + 本地强校验”。关键词只用于定位上下文，不会单独被当作能力证据。模型会判断回答中的矛盾、机制、责任边界、关键取舍、失败原因和岗位本质错配；结果和指标只在原问题核实成果、候选人主动作出成果主张或岗位存在明确 KPI 时使用，不再作为通用必填项。每条建议必须绑定当前问题、能力项、候选人片段和逐字原话。模型不可用或没有高价值追问时，追问区保持为空，不再用通用本地模板冒充理解。

使用 DeepSeek V4 时，结构化 JD 分析和实时追问请求会显式关闭长链思考模式。两类任务依靠完整上下文理解和本地证据校验，不需要消耗数千 token 输出不可见的思考过程；这样可以显著降低延迟和因输出预算耗尽导致的空响应。

模型只能提出证据候选、追问和评价摘要，不能直接修改人工评分、录用结论或候选人阶段。API Key 不会返回浏览器、写入数据库或显示在页面中。

### 飞书登录配置（部署时）

在飞书开放平台创建企业自建应用，在安全设置中加入回调地址，例如 `https://interview.example.com/api/v1/auth/feishu/callback`，然后在服务器环境变量中配置：

```powershell
$env:INTERVIEW_ENV="production"
$env:INTERVIEW_SESSION_SECRET="至少 32 字节的随机字符串"
$env:FEISHU_APP_ID="cli_xxx"
$env:FEISHU_APP_SECRET="仅保存在服务器的 App Secret"
$env:FEISHU_REDIRECT_URI="https://interview.example.com/api/v1/auth/feishu/callback"
$env:FEISHU_OAUTH_SCOPES="auth:user.id:read"
$env:FEISHU_HR_OPEN_IDS="ou_hr_1,ou_hr_2"
$env:FEISHU_ADMIN_OPEN_IDS="ou_admin_1"
```

生产环境未登录时所有业务 API 返回 401，本地预览身份入口会自动关闭。App Secret 和飞书 `user_access_token` 不会返回浏览器；系统会话 Cookie 使用 HttpOnly、SameSite=Lax，HTTPS 环境下启用 Secure。

### 飞书通知配置（部署时）

HR 后台的“飞书通知中心”会先生成排期、面试前 24 小时提醒、待补人工评价、HR 终审和知识审批的消息草稿。同一业务事件不会重复建队列；未配置时只能预览，任何消息都不会自动发送。

飞书自建应用添加“机器人”能力并取得 `im:message:send_as_bot` 应用身份权限后，在服务器配置：

```powershell
$env:FEISHU_NOTIFICATIONS_ENABLED="true"
$env:INTERVIEW_PUBLIC_BASE_URL="https://interview.example.com"
```

发送时使用服务器端 `tenant_access_token` 和候选收件人的 `open_id`，App Secret 不会返回浏览器或写入数据库。即使配置完成，也必须由 HR 勾选具体消息并再次确认；当前版本不在后台静默群发。

运行测试：

```powershell
pytest
```

### 系统配置与试点就绪中心

HR 可从“招聘任务后台”进入试点就绪中心，查看飞书登录、飞书通知、腾讯云 ASR、真实大模型、数据库、录音存储、HTTPS、会话安全、Obsidian 和北森接口的状态。页面会区分正式试点阻断项、上线调整项和可滞后项，不会把“本地能演示”误判为“可以真实上线”。

只有管理员可以执行连接测试。数据库、目录和知识库测试会验证实际可用性并清理临时文件；飞书测试只获取应用令牌、不发送消息；模型测试只发送固定的 `ready` 探针，不包含候选人信息。腾讯云 ASR 的字段完整性只能证明配置存在，正式试点前仍需用短音频验证权限、延迟和准确率。所有测试均保留操作审计，接口永远不返回密钥值。

## Obsidian 人才知识库

本地开发环境会自动识别 `D:\Interview-Knowledge`。其他电脑或服务器通过环境变量配置：

```powershell
$env:INTERVIEW_KNOWLEDGE_VAULT_DIR="D:\Interview-Knowledge"
$env:INTERVIEW_KNOWLEDGE_VAULT_NAME="Interview-Knowledge"
```

HR 后台的“人才知识库”页面用于查看待审批提案、批准并发布、处理失败重试以及打开对应的 Obsidian 文档。批准时系统只发布结构化、脱敏后的岗位知识；候选人姓名、简历、录音、逐字稿和联系方式不会写入 Vault。每次成功发布都会生成独立知识文件、版本号、SHA-256 摘要和发布记录。

自更新闭环遵循“人工确认在前”的顺序：结束面试时后端自动生成证据优先评价草稿；面试官提交人工评价后，系统才从 JD 定制问题的未覆盖或浅回答中生成题目、追问规则提案。相同岗位、轮次和问题的提案会自动聚合出现次数，不会因重复提交而重复创建。AI 不能直接写入正式 Vault，HR 审批仍是硬门槛。

### 系统使用与运维文档

产品功能、HR/面试官操作、集成配置、数据治理、部署排障和开发历程由项目内的 `docs/obsidian-system-docs` 统一维护。HR 可在“人才知识库”页面查看每份文档与 Obsidian 的版本差异，确认后同步到 Vault 的 `70-系统使用与运维` 文件夹；同步操作会写入审计记录，不在后台自动执行。

这组文档统一带有 `type: system_documentation`、`contains_pii: false` 和 `rag_scope: excluded` 元数据。它不会包含候选人数据或密钥值，也不会参与面试题生成、能力评价、人才画像或其他候选人分析；人才知识与系统说明在存储和检索边界上保持分离。

## 新岗位与 JD 建档

新岗位不需要先有岗位人才画像。HR 应先从“招聘任务后台 → 岗位与 JD”建立岗位，填写岗位名称、岗位编号和完整 JD。保存后系统会立即生成一份画像草稿，等待 HR 与业务负责人审核；草稿不会自动成为正式面试标准。

保存时系统会先对完整 JD 做岗位语义建模，提炼岗位使命、业务结果、真实工作场景和七项分轮验证维度（业务面 3 项、HR 面 2 项、CEO 面 2 项），再生成要求候选人提供情境、本人行动、结果和取舍证据的问题。性别、年龄、婚育、籍贯、特定学校、外貌或身体条件即使写进 JD，也会被标记并排除，不进入提问或人才画像。模型不可用时使用本地结构化保障，不回退到任意短词提问。

标准操作顺序是：

1. 建立岗位并录入 JD。
2. 核对系统生成的岗位人才画像草稿并人工生效。
3. 为该岗位批量导入已经通过筛选的候选人。
4. 按岗位需要选择业务面、HR 面、CEO 面中的 1–3 轮，并调整实际顺序。

更新已有岗位的 JD 时，系统会生成“JD 更新”画像草稿并刷新尚未开始的面试计划。进行中和已完成的面试冻结原标准，不会被中途改写。暂停招聘的岗位仍保留历史档案，但不能继续导入候选人或新建面试。

## 岗位人才画像版本中心

HR 先在“公司基础人才画像版本中心”维护所有岗位共同遵循的行为标准。每项公司能力包含定义、正向证据、风险信号、统一问题、追问、关键词、1/3/5 分锚点和主验证轮次。保存只形成草稿；HR 二次确认生效后，系统只刷新尚未开始的面试，并给全部岗位画像生成继承更新草稿。正在进行和已完成的面试会冻结原标准，避免会中途切换评价口径。

HR 后台也可按岗位生成第一版岗位人才画像。首版使用当前生效的公司基础画像、岗位 JD 和业务面、HR 面、CEO 面的标准能力项，不读取候选人姓名、简历或逐字稿。画像以版本管理：草稿经 HR 确认后生效，旧版本保留为历史记录，并同步发布到 Obsidian。

后续版本使用进入录用审批的聚合信号，但至少需要 3 份样本才允许生效；系统只展示人工确认能力项的聚合次数和均分，不把单个候选人的内容写入画像。录用审批不是绩效证明，因此当前更新只作为招聘标准候选版本，未来仍需用试用期或在岗绩效结果校准。

### 北森历史样本导入

在“岗位人才画像版本中心”选择岗位后，HR 可上传北森导出的 `.xlsx` 或 `.csv`，也可以先下载系统模板。导入分两步：系统先自动识别招聘结果、评价列和标准能力项，展示掩码姓名与结构化信号；HR 核对并勾选后才会写入样本池。同一岗位重复提交同一导出记录会被跳过。

历史样本只保存招聘结果、能力信号、质量标记和不可逆记录摘要，不保存姓名、手机号、邮箱、简历或面试评价原文。“录用 / 已入职 / 试用期通过”可计入三份样本门槛，其中“试用期通过”会单独标识为经过结果验证；新画像仍然只是草稿，必须由 HR 审核后生效。

## 面试质量分析

HR 登录后可从后台进入“面试质量分析”，查看标准题覆盖率、候选人表达占比、证据密度、人工评价完成率和需要辅导的面试行为。页面支持按岗位筛选，并把岗位长期招不到人的信号分为“面试流程可能需要调整”“供给或招聘标准可能需要复查”和“样本不足”。

单个面试官少于 3 场已完成面试时，系统只展示观察值并明确标记样本不足，不生成稳定结论。该看板用于改进题目、流程和培训，不能单独作为绩效、晋升或淘汰依据。

## 角色化行动中心

登录首页会按飞书身份展示“我的面试待办”：只包含当前账号被分配的今日面试、未来七天准备项和已经结束但尚未提交的人工评价。HR 招聘任务后台另有“今日行动中心”，集中展示待排期候选人、今日全部面试、待补人工评价、已满足三轮终审条件的候选人，以及待审批知识提案。

行动中心只负责把人带到正确页面，不会自动提交评价、变更候选人阶段或发布知识。候选人阶段仍只能由 HR 在三轮汇总中勾选确认后变更。

## 飞书通知中心

通知队列覆盖五类协同动作：新面试排期、面试前 24 小时提醒、面试结束待补评价、三轮评价齐备后的 HR 终审，以及人才知识提案待审批。通知中的系统链接可以在飞书登录后直接打开对应面试、终审或知识页面。

消息仅包含候选人姓名、岗位、轮次、时间和待办动作，不包含简历原文、录音、逐字稿、能力评分或录用建议。HR 可查看预约发送、待发送、成功与失败状态；失败记录保留错误原因和尝试次数，配置修复后可人工重试。

## 三轮面试报告中心

HR 可从候选人的“三轮面试汇总”生成报告草稿。报告把人工能力评分、面试官结论、跨轮分歧和已确认逐字稿证据固化为版本快照；刷新未锁定草稿会更新当前版本，锁定后再次生成会创建下一版本，旧版本保留为历史记录。

报告分为两种受众：管理层摘要只展示流程结论、关键优势、风险、分歧、能力评分和证据摘录；HR 完整档案额外展示录音/逐字稿链接、面试官质量复盘与内部治理信息。只有锁定后的管理层摘要可以复制内部链接，且打开者仍需使用公司账号登录并参与过该候选人的面试。打印页面使用 A4 版式，可通过浏览器“打印 / 保存为 PDF”。

## 数据治理与审计中心

HR 可从招聘任务后台进入“数据治理与审计”，查看已经到期、仅录音到期以及 30 天内即将到期的材料。系统默认保留 90 天，单次建档最长 180 天；首版不会在后台静默执行删除，HR 必须勾选具体候选人并完成二次确认。

候选人材料包到期后，系统删除录音文件、逐字稿和逐字稿证据，并把报告快照中的证据原话、逐字稿链接和录音入口脱敏；能力评分、各轮人工评价、最终流程决定、脱敏知识成果和审计记录继续保留。若只有录音先到期，则只清理到期录音，不提前删除逐字稿。报告锁定、最终流程决定、录音/逐字稿下载和清理操作都会记录操作者、时间与资源编号，但审计日志不会保存逐字稿内容。

## 生产边界

- 默认数据库是 SQLite，只用于开发和单机演示；设置 `INTERVIEW_DATABASE_URL` 可切到 PostgreSQL。
- `INTERVIEW_PROVIDER_MODE=mock` 时不会调用外部模型。
- 麦克风只能由面试官点击“开启麦克风”后授权，不会随页面加载自动申请。
- 本地录音写入 `backend/data/recordings/<interview_id>/`，默认被 Git 忽略。
- 当前 WebSocket 音频链路适合本地和受控网络试点；公网生产应升级为 WebRTC。
- 腾讯云话者分离引擎会先区分声源，再逐句结合问答语义判断面试官与候选人；即使云端短时复用同一声源编号，明确的提问和回答也能分别纠偏。低置信度内容保持“待确认”，人工确认始终具有最高优先级。
- 正式试点必须接入经评测的 ASR / LLM Provider，并完成候选人告知、传输与存储加密；当前已具备角色权限、关键操作审计和 HR 确认式到期清理，服务器定时清理仍待上线阶段启用。
- 系统不会自动录用、淘汰或变更北森候选人阶段。
- 知识更新只生成提案，必须由审批人发布。

## 实时副驾驶行为

- 临时字幕与最终字幕走腾讯云流式 WebSocket；语义追问在独立后台任务中运行，不阻塞后续字幕。
- 高价值浅答建议高亮并累计保留，可标记“已追问 / 暂不追问”；可当场改变判断的缺口立即出现，跨轮或外部核验事项才进入下一轮建议。
- `plan-v1.1` 每轮最多保留 1 道统一题。深度模型结合 JD 与简历原文，从候选人的真实经历追问机制、设计判断、取舍、失败边界或岗位本质；应届生可使用课程、比赛、社团、实习或个人项目作答。所有问题都必须绑定简历原文，不允许凭 JD 虚构候选人经历。
- 简历题采用“语义深度题优先、原文核实题兜底”：只有通过原文引用与岗位维度校验的模型问题才会替换基础题；模型返回空、超时或问题被过滤时，保留本地已经从简历原文与 JD 重点匹配出的 1–2 道问题，不再静默只剩统一必问题。确实找不到相关经历时，页面会明确说明，不虚构候选人经验。
- 实时追问只承接候选人已经说出的内容，每条建议同时展示对应原问题和候选人连续原话；未回答的固定题不会出现在右侧追问区。
- 腾讯云把一句话切成多个稳定片段时，系统先合并当前逻辑回答再进行语义分析；连续的面试官片段也只形成一个真实问题，避免碎片数量污染问题覆盖和评分。
- 页面使用常驻侧边栏串联首页待办、面试工作台、本轮评价和 HR 后台。结束面试后直接显示 AI 参考分与下一轮建议；待评价支持安全移出但不删除任何面试材料。
- “嗯、哦、好的、然后呢”等口头语、确认词和候选人反问不会计为回答或能力证据。信息缺失只形成评价限制；只有明确表现出的事实、判断、行动、理由、责任边界或风险行为才可进入待确认事实。
- 实时证据区会按能力项、方向、逐字稿片段和原话相似度合并重复事实，优先展示已人工确认且信息更完整的原话；每张卡会标明来源问题、影响哪项岗位判断以及是否仍待核对。合并只影响界面，所有原始证据仍完整保留以便审计。
- 未回答和回答较浅统一进入“尚待验证”，明确标注“不支持正向或反向结论”，不会与候选人已经表现出的明确风险混为一谈。
- 面试结束后分别输出岗位证据分、回答质量分、面试完整度、下一轮建议和 AI 面试质量分。漏问统一题计入面试过程缺口，不作为候选人的负面证据；所有候选人阶段变化继续保留人工确认门槛。
- 面试结束后还会独立生成“回答逻辑与一致性核验”，不依赖固定题，检查因果链、时间线、本人/团队贡献边界、成果口径与跨回答一致性。只有至少两段候选人原话直接冲突时才展示事实、时间线或责任口径冲突；单一成果主张只能标记为待验证。系统明确禁止依据语速、停顿、口音、紧张或表情判断撒谎，所有异常只生成核验问题，不直接进入录用或淘汰结论。
- 评价维度按面试职责分轮：业务面、HR 面和 CEO 面分别使用自己的通用能力与 JD 岗位证据。结束评分会分批复盘本轮全部逐字稿，预设题、临场问题和自然追问具有同等证据资格；三轮汇总再对各轮有证据的参考分等权汇总。

当前集成边界必须如实理解：

- Pipecat 目前是浏览器 PCM 到 `InputAudioRawFrame` 的帧桥，不是完整媒体流水线；
- 北森目前支持 CSV/XLSX 导出文件的预览和脱敏导入，没有接入北森在线 API；
- 飞书目前支持 OAuth 登录和人工触发通知，没有机器人自动加入飞书视频会议；
- Docker Compose 是 PostgreSQL + 应用的部署骨架，不包含正式 HTTPS、对象存储、备份、监控或密钥管理。

项目反馈先记录为 ISSUE，经用户确认形成 DECISION 后再进入实现。明确 Bug、安全问题、崩溃、测试失败或数据丢失不需要等待样本积累。每次修改只覆盖必要范围，运行相关测试与完整回归后再 commit。
